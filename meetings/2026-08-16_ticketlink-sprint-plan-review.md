## Phase 1: 전문가별 분석 (격리 병렬)

### Engineering Lead — REVISE (High 2 + 원칙 1)
재사용·아키텍처 골격(`run.ts` standalone vs `handler.ts` chat / lib 순수 vs browser Playwright / bbox 상대좌표)은 건전, 재작성 불필요.
- **High-1**: `run.ts` 프로세스/브라우저 생존주기 미명시. `launchPersistentContext`는 브라우저 수명이 Node 프로세스에 묶임(`prepare-login.ts`가 `context.on("close")→exit`로 증명). `AT_PAYMENT`가 "프로세스 종료"로 구현되면 인계 직전 라이브 세션(대기열 통과분) 소실 → 목표 붕괴. 또 보이는 크롬이 뜨려면 **LaunchAgent(Aqua GUI 세션)** 고정 필요(Daemon이면 GUI 없어 창 안 뜸).
- **High-2**: `run.lock`이 stale-lock 회수·"거부 시 알림" 미처리 → 진짜 오픈 순간 조용한 no-op(무음 미스). 플랜 자신의 "무음 실패 금지" 불변식과 충돌.
- **원칙 관찰**: 좌석도 kind 3종(dom/canvas/imagemap)은 v1이 잠실 단일 kind만 출하하므로 투기적 추상화(원칙 3). canvas RGB 샘플링·imagemap은 정찰 kind 확정 후. DSF 곱 누락 트랩.

### QA Reviewer — REVISE (High 3 + 원칙)
- **High-1**: 결제 가드가 `payment.ts` 단일 파일 스코프. 티켓링크 결제는 다단계(예매자정보→쿠폰→결제수단→약관+결제)라 봇이 중간 전진 중 간편결제 원탭을 스치면 사람 확인 없이 결제 가능. grep 게이트가 `payment.ts`만 봄 → `run.ts`·`seat-runtime.ts` 등 범용 클릭 프리미티브 미감사. 미인식 체크아웃 상태 fail-closed 규칙 없음.
- **High-2**: 인접 2석(R5) 데이터 모델·게이트·테스트 전무. VenueMap에 좌석 행/열 위상 없음 → 비인접 2석 확보→결제 도달(오예매).
- **High-3**: 안전 STOP(bbox 드리프트·빈자리 0·인접 실패)은 라이브 재현 불가인데 결정적 실패주입 테스트 부재 → "구현했으니 될 것" 의존.
- **원칙 관찰**: 좌석도 kind 투기 추상화(Eng와 수렴). allowlist-not-blocklist는 방향 옳으나 시스템 스코프로 올려야 실효.

### AI Ops Expert — REVISE (High 2 + 원칙 3)
